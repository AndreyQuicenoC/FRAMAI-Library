### 2. **Actualización del Orquestador**

**Archivo:** `.ai/workflows/user-story-implementation/orchestrator.md`

**Cambios:**
1. **Nuevo paso 5:** Clasificación de complejidad (antes de routing)
   - Calcula score de complejidad
   - Emite justificación
   - Decide políticas a cargar
   - Estima tokens
2. **Contrato compartido adaptativo:**
   - TRIVIAL: Mínimo o no necesario
   - SIMPLE: Ligero (API + errores)
   - MODERATE/COMPLEX: Completo
3. **Matriz de responsabilidades:**
   - Solo si MODERATE/COMPLEX
   - TRIVIAL/SIMPLE: Descripción textual suficiente
4. **Handoffs optimizados:**
   - NO repetir contexto completo
   - Solo información necesaria para cada agente
5. **Output adaptativo:**
   - Incluye complejidad, políticas a cargar, tokens estimados
   - Secciones condicionales según complejidad

## 🎯 Respuestas a Preguntas Clave

### ¿Vale la pena la sofisticación?

**Respuesta: Depende de la complejidad.**

- ✅ **MODERATE/COMPLEX:** Absolutamente (mejor calidad, menos retrabajo)
- ⚠️ **SIMPLE:** Sí, con pipeline ligera (v2.1.0)
- ❌ **TRIVIAL con pipeline completa:** No (v2.0.0 era ineficiente)
- ✅ **TRIVIAL con agente único:** Sí (v2.1.0 optimizado)

### ¿Consumirá demasiado?

**Respuesta: No, con estrategia adaptativa.**

- **v2.0.0:** ~50K promedio por HU (alto)
- **v2.1.0:** ~35K promedio por HU (competitivo)
- **Comparación:** Cursor típico ya usa 20-40K tokens por chat
- **Ventaja:** Mejor calidad + trazabilidad en rango similar

### ¿Vale la pena para tesis?

**Respuesta: Absolutamente.**

**Aportes académicos:**
1. ✅ Estrategia adaptativa multiagente (innovación)
2. ✅ Sistema de clasificación de complejidad (cuantificable)
3. ✅ Métricas empíricas (tokens, calidad, retrabajo)
4. ✅ Framework reproducible y versionado
5. ✅ Análisis comparativo (v2.0.0 vs v2.1.0)

**Pregunta experimental valiosa:**
> *"¿Cuánto mejora la calidad al incrementar especialización, y cuál es el coste adicional?"*

**Respuesta v2.1.0:**
- Calidad: +5-10% en MODERATE/COMPLEX
- Coste COMPLEX: +38% tokens, pero -60% retrabajo → **ahorro neto**
- Coste TRIVIAL/SIMPLE: -60-84% tokens, calidad igual

### ¿Es necesario .cursor/rules/?

**Respuesta: Sí, es útil.**

**Razón:**
- Cursor puede cargar reglas automáticamente
- Facilita uso del ecosistema desde IDE
- No es redundante (referencia rápida)

**Estado:** Actualizado a v2.1.0, no eliminado.

## 🚀 Cómo Usar

### Para HU nueva

1. **Copiar template:** `.ai/templates/user-story-implementation/full-stack.md`
2. **Completar HU** con criterios de aceptación
3. **Pegar en Cursor Agent** (Cmd/Ctrl+L)
4. **Dejar que Orquestador clasifique:**
   - Complejidad: TRIVIAL/SIMPLE/MODERATE/COMPLEX
   - Routing: FRONTEND_ONLY/BACKEND_ONLY/FULL_STACK
   - Políticas a cargar
   - Tokens estimados
5. **Revisar output del Orquestador:**
   - Si estimado < 30K tokens: Ejecutar directamente
   - Si estimado 30-70K tokens: Revisar plan
   - Si estimado > 70K tokens: Validar necesidad pipeline completa
6. **Ejecutar pipeline según plan**
7. **Revisar 4 documentos actualizados:**
   - `docs/user-stories.md`
   - `docs/code-structure.md`
   - `docs/implementation-report.md`
   - `docs/integration-report.md` (si MODERATE/COMPLEX)

### Para optimizar consumo

1. **Confiar en clasificación automática** del Orquestador
2. **No forzar pipeline completa** para HUs simples
3. **Revisar tokens estimados** antes de ejecutar
4. **Ajustar umbrales** de complejidad si necesario (en `adaptive-policies.md`)
